## 0. 结论摘要

**实施策略：先复刻 Modrinth App 的 launcher 窗口，后续再基于对比改造。**
本文档记录复刻目标、结构依据，以及一个被推翻的判断（§4.2.3）作为纪律留档。

启动器窗口的问题**不是样式不好看，是缺一层抽象**。

主进程早就按「每个版本一个游戏目录」组织文件（`game/<versionId>/`、`versions/<versionId>/mods/`），
这在物理上已经是「实例」。但代码里**没有实例抽象** —— 没有注册表、没有元数据、没有分组，
`selected` 只是个版本号字符串。于是实例被降维成一个下拉框，六个互不相干的区块平铺在一条滚动条上，
核心动作「启动游戏」沉到第 524 行。

三个成熟启动器的 UI 都建立在「实例是一等公民」之上，但分两个流派：

- **Prism Launcher / HMCL** —— 多实例管理派（左列表右详情、固定启动按钮）
- **Modrinth App** —— 内容优先派（快速开始卡片自带启动按钮 + 实例库网格）

我们取两派的**共识**（实例一等公民、启动入口恒可见、状态有徽章、错误有统一位置），
路线走 Modrinth —— 因为我们是生成内容的工具，`packages` 面板已承担内容发现，
启动窗口该以「跑」为主角而非「管」为主角。详细取舍见 §4.2.3。

## 1. 现状清点：这个界面现在有哪些

`GameLauncherPanel.tsx`（539 行），自上而下：

| #   | 区块                                              | 行号                  | 性质               | 依赖「实例」吗             |
| --- | ------------------------------------------------- | --------------------- | ------------------ | -------------------------- |
| 1   | 选择版本（下拉 + 刷新）                           | 262–294               | **选目标**         | 是（它就是实例的替代品）   |
| 2   | 启动配置（用户名 / 内存）                         | 296–319               | 可选               | 否（全局）                 |
| 3   | 加载器安装（Fabric / NeoForge）                   | 321–345               | 前置条件           | 是（装到 `versions/<v>/`） |
| 4   | 已装 Mod（列表 + 刷新 / 删除）                    | 347–~400              | 可选               | 是（`versions/<v>/mods`）  |
| 5   | 离线已有安装（定位 / 选目录 / 装 Mod / 启动安装） | ~400–430              | **另一条启动路径** | 是（外部目录）             |
| 6   | 使用说明（6 行静态文案）                          | 528–533               | 静态               | 否                         |
| 7   | **下载客户端 / 启动游戏**                         | **496–524（最底部）** | **核心动作**       | 是                         |

### 1.1 三个结构性问题

**① 核心动作沉底。** 「启动游戏」在第 524 行。进到这个面板的第一眼看不到它，
得先滚过 5 个区块。HMCL 社区讨论自己 UI 时的那句评价几乎适用于此处：

> 「UI 整体看来**重点不够突出**」（HMCL issue #3683）

**② 三条启动路径被压进同一条滚动条。** 它们的流程根本不同：

| 路径                | 入口                                           | 数据来源                      |
| ------------------- | ---------------------------------------------- | ----------------------------- |
| A. 下载的版本       | `LAUNCHER_DOWNLOAD` + `LAUNCHER_LAUNCH`        | `versions/<v>/` + `game/<v>/` |
| B. 离线已有 MC 目录 | `LOCATE_MC` / `MC_CHOOSE_DIR` / `LAUNCH_MC`    | 外部已存在的 MC 目录          |
| C. 项目产出的 jar   | `jarPath`（`mod-store` 里 `files.find(.jar)`） | 当前项目构建产物              |

C 路径甚至没有独立的操作按钮 —— 它只是把 `jarPath` 显示在区块 5 里，
让人手工点「安装 Mod（需先构建）」。**项目产物无法一键启动**，这是功能缺口不只是布局问题。

**③ 「下载」与「启动」是两个平级按钮。** 用户要启动游戏，前置是「先下载客户端」，
但界面上两者平级，用户得自己判断顺序和当前状态。
HMCL 的做法是**一个按钮自己吃掉这个状态**（见 §2.2）。

### 1.2 没有任何折叠能力

`collapsed` / `expanded` / `details` / `summary` / `Accordion` 在该文件出现次数**全为 0**。
六个区块一律平铺，可选项（启动配置 / 皮肤 / 使用说明）与必选项同权。

## 2. 实证对照：成熟启动器怎么做

> 本节全部来自可查证的一手来源，不是印象。

### 2.1 Prism Launcher（源码）

来源：`PrismLauncher/PrismLauncher` 的 `launcher/ui/MainWindow.cpp`、`InstanceWindow.cpp`、`MainWindow.ui`

| 做法                                             | 证据                                                                                                                                                |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **实例列表在左，详情在右**                       | `view = new InstanceView(ui->centralWidget)` → `ui->horizontalLayout->addWidget(view)`                                                              |
| **启动按钮锚定在固定竖向工具条，永不被滚动埋没** | `ui->instanceToolBar->setOrientation(Qt::Vertical)`；`actionLaunchInstance` 常驻其中                                                                |
| **启动是 split button**                          | `m_launchButton->setPopupMode(QToolButton::MenuButtonPopup)` + `populateLaunchMenu(launchMenu)` —— 主键启动，箭头选启动方式（离线 / 测试 / 服务器） |
| **可用性由选中实例派生**                         | `ui->actionLaunchInstance->setEnabled(m_selectedInstance->canLaunch())`                                                                             |
| **实例分组且可折叠**                             | `VisualGroup`、`groupStateChanged`、`APPLICATION->instances()->isGroupCollapsed(groupName)`                                                         |
| **可排序：按名 / 按最近启动**                    | `actionCAT` 旁的 `sortByNameBtn` / `sortLastLaunchedBtn`（`InstSortMode`）                                                                          |
| **双击实例即启动**                               | `connect(view->activated, &MainWindow::instanceActivated)`                                                                                          |
| **右键菜单**                                     | 重命名 / 改图标 / 换组 / 编辑 / 打开目录 / 删除 / 复制 / 导出（zip / mrpack / flame）                                                               |
| **Kill 独立成键**                                | `actionKillInstance`，快捷键 `Ctrl+K`                                                                                                               |

**最关键的一条**：Launch 在**固定工具条**里，不在可滚动内容里。
这不是审美选择 —— 它保证「启动」这个动作在任何滚动位置都可达。

### 2.2 HMCL（官方文档）

来源：`docs.hmcl.net/launcher/gui-features.html`

首页结构：

```
首页 = 侧边导航栏 + 提示面板（仅开发/预览版） + 更新面板（仅有更新时） + 启动游戏面板
```

**启动游戏面板**的官方定义：

> 此区域共分为两部分：启动（开始）游戏按钮、切换实例菜单。
>
> **启动（开始）游戏按钮**：若用户当前存在实例，点击后则会启动当前应用的游戏实例；
> **若当前不存在游戏实例，点击后会自动下载最新正式版然后启动游戏。**
> **切换实例菜单**：点击显示快捷切换游戏实例列表菜单。

侧边栏「实例管理」项：

> 该项会显示当前选定的游戏实例图标及名称。用户点击该项后进入实例管理页面；
> **在该项上滚动鼠标滚轮可在不同游戏实例之间进行快捷切换。**

另有「简洁版 UI」模式：隐藏左侧栏，改为底部导航栏（`SimpleUI` / `Compact Mode`）。

**最关键的两条**：

1. **启动按钮与「切换实例」是两个分开的控件**，不是一个大按钮带下拉。
   HMCL 社区讨论里明确肯定这个拆分：「在『开始游戏』将箭头和主按钮分开是正确的」。
2. **启动按钮自己处理「还没装」的状态** —— 不需要用户先点下载。

### 2.3 Modrinth App（第三样本：内容优先派）

Modrinth App 与 Prism / HMCL **不是同一流派**，这点必须先分清，否则会抄错。

|              | Prism / HMCL                   | Modrinth App                         |
| ------------ | ------------------------------ | ------------------------------------ |
| 中心是什么   | **多实例管理**（装了几个游戏） | **内容发现 → 安装 → 玩**             |
| 首页干什么   | 选实例、启动                   | 给最近要玩的几张卡，每张自带启动按钮 |
| 实例库的角色 | 主角                           | 一堆卡片的网格                       |
| 适合谁       | 10+ 整合包的重度玩家           | 想玩新整合包的人                     |

它的首页结构（据界面截图）：

```
左侧 icon rail（发现 / 模组 / 资源包 / 数据包 / 光影 / 服务器 …）
└─ 其中一个位置是当前实例的头像 → 兼作实例切换器

顶部栏：logo · 前进后退 · 页面标题 · 账号
内容区：
  ① 全局状态横幅（「无法连接到身份验证服务器」）
  ② 快速开始（可折叠）
       卡片：图标 + 名称 + 「新实例」徽章
             副标题「Fabric 26.3 · 从未游玩过」
             右侧：[▶ 开始游戏]  [⋮]
  ③ 实例库
       [搜索框] [⊞新建分组] [+新建实例]
       [最后游玩时间 ▾] [自定义组 ▾] [添加筛选]
       网格卡片：图标 + 名称 + 「Fabric 26.2」
  ④ 两段之间的可拖拽分隔条
```

**关键观察**：

- 启动按钮出现在**卡片内部**，不必先选中实例
- 每实例状态徽章（`从未游玩过` / `N 天前`）是 `lastLaunchedAt` 的 UI 投影
- 左侧 rail 把「当前实例」直接做成一个头像位，切换实例不需要进二级页
- 错误有统一横幅位，不散落在各卡片里

**它的三处不足（我们不抄）**：

1. 快速开始卡片有启动按钮、实例库卡片没有 —— 同一对象两种交互
2. 「快速开始」的入选规则未说明，用户猜不到为什么是这两张
3. 快速开始区占大量垂直空间，要往下滚才够到实例库

**我们与它的关系**：我们的 `packages` 面板已经在做内容发现（Modrinth 的第 ② 段），
所以**不抄它的内容浏览部分**，只借鉴启动区与实例库的组织方式。

### 2.4 三个启动器的共同范式与分歧

| 维度               | Prism                | HMCL               | Modrinth App             | 我们现在                  |
| ------------------ | -------------------- | ------------------ | ------------------------ | ------------------------- |
| 实例是不是一等公民 | 是（`BaseInstance`） | 是（实例管理页）   | 是（头像位 + 实例库）    | ❌ 只有版本字符串         |
| 中心是什么         | 多实例管理           | 多实例管理         | 内容发现 → 玩            | ❌ 无中心                 |
| 列表 / 详情分离    | ✅ 左列表右详情      | ✅ 侧栏进详情页    | 卡片内聚，不分离         | ❌ 单列滚动               |
| 启动按钮位置       | 固定工具条，恒可见   | 首页常驻面板       | 卡片内，恒可见           | ❌ 沉在第 524 行          |
| 启动按钮处理未安装 | `canLaunch()` 置灰   | **自动下载后启动** | 「新实例」徽章引导       | ❌ 两个平级按钮           |
| 卡片自带启动入口   | ❌（在工具条）       | ❌（在启动面板）   | ✅ 快速开始有 / 实例库无 | ❌                        |
| 每实例状态徽章     | ❌                   | ❌                 | ✅ 从未游玩过 / N 天前   | ❌                        |
| 统一错误横幅       | 状态栏               | 弹窗               | ✅ 顶部横幅              | ❌ 散落各区块             |
| 实例可分组         | ✅                   | ✅                 | ✅                       | ❌                        |
| 排序               | 按名 / 按最近启动    | 按最近启动         | 按最后游玩时间           | ❌                        |
| 重复启动的并发处理 | `isRunning()` → Kill | 冷却时间           | 未见                     | ⚠️ 只有 `runningPid` 置灰 |

**共识（三个都有，我们缺）**：实例是一等公民、启动入口恒可见、状态有徽章、错误有统一位置。
**分歧**：Prism/HMCL 把实例管理当主角，Modrinth 把内容发现当主角。
我们取「共识」全盘，路线取 Modrinth（因为我们是生成内容的工具，详见 §4.2.3）。

## 3. 根本差异：我们有实例的物理结构，没有抽象

主进程 `launcher-service.ts` 的事实：

```ts
:307   const gameDir = opts.gameDir || join(this.baseDir, 'game', detail.id)
:454   return join(this.baseDir, 'versions', version, 'mods')
:202   const jarPath = join(this.baseDir, 'versions', detail.id, `${detail.id}.jar`)
```

目录布局：

```
userData/mc-launcher/
├── versions/<versionId>/<versionId>.jar    客户端 jar
├── versions/<versionId>/mods/               ← 独立 Mod 目录
├── assets/                                   全局共享（hash 存储）
├── libraries/                                全局共享
└── game/<versionId>/                         ← 独立游戏目录（存档、世界、配置）
```

**`game/<versionId>/` + `versions/<versionId>/mods/` 就是一个实例。** 但：

- 没有实例注册表（`instances.json` 之类）
- 没有实例元数据（图标、名称、创建时间、最近启动时间、内存配置、Java 路径）
- 没有「哪些版本已经下载过客户端」的索引 —— 每次都要 `existsSync` 现算
- 没有分组
- 用户配置（用户名 / 内存）是**组件局部 state**，切面板就没了

全仓 `instance` 命中 36 处，**全部是 JS 的 `instanceof` 关键字**，与「游戏实例」无关。

## 4. 目标架构

### 4.1 数据层：实例注册表

新增 `userData/mc-launcher/instances.json`：

```ts
interface InstanceRecord {
  id: string; // = versionId，一对一，作为主键
  name: string; // 显示名，默认 = versionId，可改
  versionId: string;
  loader: 'vanilla' | 'fabric' | 'neoforge';
  gameDir: string; // 默认 join(baseDir,'game',versionId)
  memory: string; // 实例级，覆盖全局
  javaPath?: string; // 实例级
  iconKey?: string;
  group?: string;
  createdAt: number;
  lastLaunchedAt?: number; // 支撑「按最近启动排序」
}
```

**迁移策略**：首次运行时扫描 `game/*` 与 `versions/*`，
为每个「jar 已存在」的版本生成一条记录（`name = versionId`，其余用默认值）。
用户无感知，不需要手动操作。

**新增 IPC**（全部幂等，缺失即视为空实例表）：

| 通道                       | 用途                                                      |
| -------------------------- | --------------------------------------------------------- |
| `LAUNCHER_LIST_INSTANCES`  | 列出实例（含 `clientReady: boolean`，避免渲染层逐个探盘） |
| `LAUNCHER_CREATE_INSTANCE` | 由版本号创建实例                                          |
| `LAUNCHER_UPDATE_INSTANCE` | 改元数据（名称 / 内存 / 分组 / 图标）                     |
| `LAUNCHER_DELETE_INSTANCE` | 删记录（**不删磁盘**，另设「同时删除文件」）              |
| `LAUNCHER_LAUNCH_INSTANCE` | 统一启动入口，内部按就绪状态决定是否先下载                |

### 4.2 界面层：三条路径的主次关系

> **本节在 §2.4 加入 Modrinth App 样本后已修订。** 原方案是 Prism 式的
> 「左列表 + 右详情 + 顶部常驻启动条」，现改为 Modrinth 式的
> 「快速开始 + 实例库」两段式。修订理由见 §4.2.3。

```
┌──────────────────────────────────────────────────────────────┐
│ 游戏启动器                                    离线模式 · …   │  面板头
├──────────────────────────────────────────────────────────────┤
│ ⚠ 统一错误横幅（下载失败 / Java 缺失 / 目录无权限）           │
├──────────────────────────────────────────────────────────────┤
│ 快速开始 ⌃（可折叠）                                          │
│  ┌────────────────┐  ┌────────────────┐                     │
│  │ (FO)  新实例    │  │ (⬚)  新实例    │                     │
│  │ Fabulously…     │  │ [SUC] Survival…│                     │
│  │ Fabric 26.3     │  │ Fabric 26.2    │                     │
│  │ 从未游玩过       │  │ 3 天前玩过      │                     │
│  │  [▶ 开始游戏] ⋮ │  │  [▶ 开始游戏] ⋮│                     │
│  └────────────────┘  └────────────────┘                     │
├──────────────────────────────────────────────────────────────┤
│ 实例库  [🔍 搜索] [最后游玩时间 ▾] [自定义组 ▾]               │
│                                  [⊞ 新建分组] [+ 新建实例]  │
│  ┌────┐ ┌────┐ ┌────┐ ┌────┐                                 │
│  │ ⬚  │ │ FO │ │ …  │ │    │  ← 网格卡片                    │
│  └────┘ └────┘ └────┘ └────┘                                 │
│      ↑ 每张卡片也带启动按钮（见 §4.2.4）                      │
├──────────────────────────────────────────────────────────────┤
│ ▸ 使用已有的 MC 安装（次要入口，默认收起）                    │
│ ▸ 从项目产物启动（需先构建）                                  │
└──────────────────────────────────────────────────────────────┘
```

选中某个实例后，下方展开**实例详情**区（启动配置 / 加载器 / Mod 列表）——
即 §1 清点里的区块 2、3、4 收拢到这里，不再与快速开始平铺争首屏。

#### 4.2.1 与三个样本的对应

| 我们的结构     | 来自         | 具体做法                                                         |
| -------------- | ------------ | ---------------------------------------------------------------- |
| 错误横幅       | Modrinth App | 顶部全宽横幅，承载下载失败 / Java 缺失 / 目录无权限              |
| 快速开始       | Modrinth App | 卡片自带启动按钮 + kebab 菜单；徽章显示「从未游玩过」/「N 天前」 |
| 实例库         | Modrinth App | 搜索 + 排序（最后游玩时间）+ 分组筛选 + 网格                     |
| 次入口         | 本次主动决策 | 路径 B / C 降级为默认收起的折叠区                                |
| 启动按钮状态机 | HMCL         | 一个按钮吃掉「未下载 → 自动下载 → 启动」                         |

#### 4.2.2 从 Modrinth 学的三点

**① 快速开始卡片自带启动按钮。** 卡片自足：名字、版本、状态一目了然。
比 Prism 的「左列表选中 → 右详情按启动」更适合我们 ——
我们的实例数大概率很少（多数用户 1–3 个），列表式选择器在这种量级是过度设计；
且 launcher 域下左栏已被 `needsFileTree` 收起（工作台文档 §1.11），中栏占满宽度，横向排卡片正好。

**② 每实例状态徽章。** `Fabric 26.3 · 从未游玩过` 是注册表 `lastLaunchedAt` 的 UI 投影。
我们目前完全没有这个概念（用户名 / 内存还是组件局部 `useState`，切面板就丢）。

**③ 全局状态横幅。** 现在下载失败、Java 缺失、目录无权限这些错误散落各区块，没有统一位置。

#### 4.2.3 复刻优先，不做预防性「修正」

> **本节记录一次被推翻的判断，保留在文档里作为纪律。**

本文档早期版本曾基于 Modrinth 的**界面截图**提出三处「修正」：

| 当时认为的问题                     | 拟采取的修正                 |
| ---------------------------------- | ---------------------------- |
| 快速开始卡片有启动按钮、实例库没有 | 两处都给                     |
| 「快速开始」入选规则未说明         | 自己定义规则并标注           |
| 左侧整条 icon rail                 | 不抄（我们已有 ActivityBar） |

**前两条已作废。** 理由：我看到的只是**静态截图**。那个按钮完全可能 hover 才出现、
或点了卡片才出现在别处；「规则未说明」也可能是截图没拍到说明。
**拿一张截图去「修正」一个经过真实用户验证的产品，证据方向是反的。**

现定策略：

1. **先复刻**，得到一个已知可用的基线；
2. 后续要改也是**有对比地**改 —— 拿我们的实机与 Modrinth 并排看，
   确认哪边真的更好，而不是凭推测先改一轮再回头验证。

**第三条保留，但理由要改**：不是「Modrinth 做得不好」，
而是**我们的结构性约束** —— 工作台已有 ActivityBar，再加一条 icon rail 是重复。
这条与「复刻」不冲突：我们复刻的是 launcher 窗口**内部**的结构，不是整个应用外壳。

#### 4.2.4 次入口为何降级

HMCL 侧栏把「实例管理 / 实例列表 / 下载」分三个列表项，我们受三栏布局所限不能加侧栏项。
理由：路径 B（用自己已有的 MC）是**低频**场景，不该和主路径争首屏。

### 4.3 实例详情：五个 tab（已决策全做）

Modrinth 的实例详情用 tab 分区（内容 / 文件 / 世界 / 日志 / 分享），
这正好回答了 §4.2 留下的盲点 —— 「选中实例后详情区里怎么组织」。

**已决策：五个全做。** 结构：

```
┌──────────────────────────────────────────────────────────────┐
│ [⬚] 实例名（粗体）                        [▶ 开始游戏] [⚙] [⋮] │ ← 常驻栏
│      🔗 Fabric 26.2 · 🕐 从未玩过                                │
├──────────────────────────────────────────────────────────────┤
│  内容 │ 实例目录 │ 世界 │ 日志 │ 分享                          │
├──────────────────────────────────────────────────────────────┤
│  （选中 tab 的内容）                                            │
└──────────────────────────────────────────────────────────────┘
```

**现成红利**：我们已有 `DomainTabs`（中栏 tab 条）与 `MiddlePanel`（5 tab 的 IDE 外壳），
这套 tab 机制可直接复用，不新造。

#### 4.3.1 五个 tab 各自需要补的主进程能力

**这是「五个全做」的真实成本，逐条核过现状：**

| tab          | 现状                                                                              | 需要新增                                           |
| ------------ | --------------------------------------------------------------------------------- | -------------------------------------------------- |
| **内容**     | `listMods` / `installMod` / `removeMod` 已有（`launcher-service.ts:458/469/479`） | **启用/禁用**（现在只能删，没有 disable）          |
| **实例目录** | 无                                                                                | **列目录**；且需与项目文件树区分                   |
| **世界**     | 无                                                                                | **列存档**：读 `game/<v>/saves/`、解析 `level.dat` |
| **日志**     | 无                                                                                | **捕获游戏输出** —— 见下                           |
| **分享**     | `export` 面板有部分能力                                                           | 导出为 `mrpack` / CurseForge 格式                  |

**日志 tab 的根因**（已核实）：

```ts
launcher-service.ts:344   spawnImpl(java, args, { stdio: 'ignore' })   ← 游戏进程
launcher-service.ts:408   { stdio: 'ignore' }                          ← fabric installer
launcher-service.ts:438   stdio: 'ignore'                              ← neoforge installer
```

三处 `stdio: 'ignore'` —— **游戏的 stdout/stderr 被直接丢弃**。
所以现在启动游戏后玩家看不到任何日志，游戏崩了也不知道原因。
做「日志」tab 的第一步是把它改成 `pipe` + 逐行转发到渲染层。

> **可复用的先例**：服务端（`src/main/ipc/kernel.ts:150`）已有
> `hasLogs: existsSync(join(dir, 'logs', 'latest.log'))` 的日志探测。
> 游戏侧可以直接沿用同一套「读 `logs/latest.log`」的能力，不必另发明明。
> 注意 `process-supervisor.ts` 里那 42 处 `crashed` 是**服务端进程状态**
> （`ServerState = 'stopped'|'starting'|'running'|'stopping'|'crashed'`），
> 与游戏侧日志无关，别误当成已有能力。

#### 4.3.1a 日志 tab 的界面（据 Modrinth 实例详情「日志」页）

Modrinth 的日志页结构：

```
┌──────────────────────────────────────────────────────────────┐
│ [搜索日志…………………………]                    [ Live Log ▾ ]  │
│ [🔽] [All] [Error] [Warn] [Info]              [⛶ 展开]      │
├──────────────────────────────────────────────────────────────┤
│  /                                                        ┐  │
│  |  Start your instance in the top right to start         |  │  ← 空态引导
│  |  receiving live logs!                                  |  │
│  \                                                        ┘  │
│   （Modrinth ASCII logo 逐字符动画 = 等待游戏启动）           │
└──────────────────────────────────────────────────────────────┘
```

**四处值得照做的地方**（我原设计只写了机制，没写界面）：

**① 日志有三个来源，不是一个。** `Live Log ▾` 是模式选择器，
对应 MC 标准目录里的三类日志：

| 来源     | 位置                                 | 用途           |
| -------- | ------------------------------------ | -------------- |
| 实时     | 进程 stdout/stderr（`pipe`）         | 游戏运行中看   |
| 最近一次 | `game/<v>/logs/latest.log`           | 游戏已关后回看 |
| 崩溃报告 | `game/<v>/crash-reports/crash-*.txt` | Java 异常栈    |

只做实时是不够的 —— 游戏一关日志就跟着没了，用户想复盘刚才那次崩溃怎么办。

**② 级别筛选（All / Error / Warn / Info）。** 纯文本搜索不够用，
MC 日志有标准级别（`[ERROR]` / `[WARN]` / `[INFO]`），应支持按级别过滤。

**③ 空态明确指向顶栏的启动按钮。**

> Start your instance in the top right to start receiving live logs!

这与本项目修 `FileTree` 空态时用的是**同一套逻辑**（工作台文档 §1.10.5）：
空态要告诉用户下一步能点哪里，而不是只说「暂无数据」。
我们对应文案：「在右上角点击『开始游戏』以接收实时日志」。

**④ 日志区可全屏展开**（`⛶`）。异常堆栈很长，中栏宽度不够看。

**另注**：Modrinth 在日志页仍保留顶栏的「开始游戏」按钮 ——
印证「启动入口恒可见」。我们 launcher 域默认不显示文件树、中栏满宽，这条天然满足。

#### 4.3.2 「实例目录」为何要改名而非叫「文件」

项目里已经存在两棵文件树，命名必须能区分：

| 名称                     | 位置            | 内容                             | 归属     |
| ------------------------ | --------------- | -------------------------------- | -------- |
| **项目文件**（左栏）     | 工作台左栏      | 生成的 mod 代码 / 资源 / 数据包  | **项目** |
| **实例目录**（详情 tab） | 实例详情内      | `game/<v>/` 下的 Mod、配置、存档 | **实例** |
| 内容浏览                 | `packages` 面板 | Modrinth 上的内容                | **远端** |

三者的读写对象完全不同（项目 / 本地实例目录 / 远端仓库）。
沿用 Modrinth 的「文件」二字会与我们已有的「项目文件树」在用户心智里撞车，
所以**明确命名为「实例目录」**，并在 tab 上标注所属实例名。

#### 4.3.3 内容 tab：只有一套搜索面

Modrinth 的内容 tab **自己不在本地搜 Modrinth**。重读其界面可确认：

```
附加内容
[🔍 搜索到 1 个项目...]        [📁 上传文件] [📋 浏览内容]
[名称 A-Z ▾] [筛选] [全部] [资源包] [+ 筛选过滤]
                          更新所有  ↻ 刷新
```

搜索框占位符是「**搜索到 1 个项目…**」—— 它在**过滤已装内容**（该实例只有 1 个），
真正去 Modrinth 找东西的是 `[📋 浏览内容]` 按钮。
**所以 Modrinth 并没有两套搜索 UI**，只有一套（在「发现」页），内容 tab 只是带目标实例的入口。

我们照此设计，**不新增第二套搜索**：

```
packages 面板（全局，唯一搜索面）
  ├─ 搜索 / 筛选 / 排序 Modrinth
  └─ 每个结果 → 「安装到…」选实例（或新建实例）

实例详情 · 内容 tab（当前实例已装）
  ├─ 搜索框：只过滤已装的
  ├─ [📁 上传文件]：本地 jar
  ├─ [📋 浏览内容]：跳 packages，并带上「目标实例 = 当前实例」
  ├─ 每行 [开关] 启用/禁用 + 🗑 删除
  └─ 更新所有 / 刷新
```

**顺带修掉一处现存断链**：现在 `packages` 搜到 Mod 后的提示是
「复制文件 URL 后在此安装」，需要用户手工复制粘贴 URL（`GameLauncherPanel.tsx:362`）。
改成「安装到…」直接选实例后，这条断链消失。

### 4.5 启动按钮的状态机

对齐 HMCL 的「自动下载后启动」，用**一个按钮**表达四种就绪态：

| 状态   | 判据                     | 按钮           | 点击后                   |
| ------ | ------------------------ | -------------- | ------------------------ |
| 无实例 | `instances.length === 0` | 建立第一个实例 | 进 ③ 引导选版本          |
| 未下载 | jar 不存在               | 下载并启动     | 先下载，进度显示在按钮内 |
| 就绪   | jar + assets + libs 齐   | **启动游戏**   | 直接启动                 |
| 运行中 | `runningPid !== null`    | 停止（PID）    | kill                     |

判据由 `LAUNCHER_LIST_INSTANCES` 一次返回（`clientReady` 字段），
**不在渲染层逐实例探盘** —— 否则实例多了会 N 次 IPC 往返。

### 4.6 与工作台其它部分的边界

- 启动器**不消费项目文件** → `needsFileTree` 保持不标（§1.11 已确立）
- 实例 = 一个可运行的 MC 环境；**项目 ≠ 实例**。项目是「内容的来源」，
  通过次入口的「从项目产物启动」与实例关联。这条边界必须写清，
  否则会重演 `explorer` 那种「一个概念三处语义」的冲突（见工作台文档 §1.10.2）。
- **三套「文件」概念必须靠命名区分**（详见 §4.3.2）：项目文件（左栏）/
  实例目录（详情 tab）/ 内容浏览（packages 面板）。

## 5. 分阶段实施

| 阶段    | 内容                                                                    | 可独立验证                                                                                                         |
| ------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| L1      | 实例注册表 + 迁移扫描 + 4 个 IPC                                        | 主进程单测：迁移幂等、空表、CRUD                                                                                   |
| L2      | 渲染层换成「快速开始 + 实例库」两段式 + 统一错误横幅                    | 组件测试：四态按钮、卡片自带启动、未下载项灰显、快速开始入选规则                                                   |
| L3      | 三条路径降级为次入口折叠区；补「从项目产物启动」                        | 集成测试                                                                                                           |
| L4      | 实例元数据编辑（名称 / 内存 / 分组 / 图标）+ 详情区 tab 骨架            | 复用 L1 的 update IPC；tab 切换与 `DomainTabs` 一致                                                                |
| L5      | 用户名 / 内存从组件局部 `useState` 迁到注册表（当前切面板就丢）         | 持久化测试                                                                                                         |
| **L6**  | **内容 tab**：启用/禁用 Mod、上传本地 jar、跳 packages 带目标实例       | 单测：disable 语义；集成：安装到指定实例                                                                           |
| **L7**  | **日志 tab**：三来源（实时 / 最近一次 / 崩溃报告）+ 级别筛选 + 全屏展开 | 主进程单测：spawn 改 `pipe`、读 `logs/latest.log`、列举 `crash-reports/`；渲染层：级别过滤、指向启动按钮的空态文案 |
| **L8**  | **实例目录 tab**：列 `game/<v>/`，与项目文件树视觉区分                  | 单测：目录列举与越界防护                                                                                           |
| **L9**  | **世界 tab**：列 `game/<v>/saves/`，解析 `level.dat`                    | 单测：存档解析、损坏 level.dat 容错                                                                                |
| **L10** | **分享 tab**：导出 mrpack / CurseForge                                  | 往返测试：导出后可被对应格式解析                                                                                   |

**依赖关系**：

```
L1 ──► L2 ──► L3
 └──► L4 ──┬──► L6（内容）
           ├──► L7（日志）    ← L7 建议提前，它修的是一个现存缺陷
           ├──► L8（实例目录）
           ├──► L9（世界）
           └──► L10（分享）
L5 独立
```

**三点说明**：

1. **L1 是地基**，不做完 L2 会返工 —— 渲染层依赖 `clientReady`、`lastLaunchedAt`。
2. **L5 单独列出**，因为它不在依赖链上，但它是「实例是一等公民」的必要条件：
   配置存在组件局部 state 里的用户偏好，严格说还是「这个面板的用户」而非「这个实例的」。
3. **L7（日志）建议提到 L6 之前**。它不是新功能而是**修缺陷** ——
   现在游戏崩溃对用户完全不可见（`stdio:'ignore'`），
   这个损失比缺一个 tab 更大。

## 6. 待定问题

**已决策（本轮）**：

- 实例详情的 tab 范围 → **五个全做**（内容 / 实例目录 / 世界 / 日志 / 分享）
- 「文件」tab 的命名 → **「实例目录」**，与项目文件树明确区分
- 内容添加入口 → **只有一套搜索面**（`packages`），内容 tab 带目标实例跳过去

**仍待定**：

1. **实例与项目的关系**：一个项目可以对应多个实例吗？还是一对一？
   物理上 `game/<versionId>/` 与项目无绑定关系，倾向「多对多，由用户手动关联」。
2. **删除实例的破坏性**：默认只删记录，还是同时删 `game/<v>/` 里的存档？
   倾向默认不删，二次确认。
3. **Java 运行时**：现在只有全局 `JAVA_HOME`。实例级 Java 路径要不要现在做？
   倾向留到 L4 之后，Prism 也是在实例设置里才暴露。
4. **「从项目产物启动」的形态**：是把构建产物**复制**进实例的 mods 目录，
   还是**软链**？复制简单但双份占用，软链干净但 Windows 需要权限。
5. **日志的落盘策略**：实时日志经 `pipe` 转发后要不要自己也落盘？
   MC 本身会写 `game/<v>/logs/latest.log` 与 `crash-reports/`，
   倾向**不重复落盘**，直接读 MC 自己写的（少一份 I/O，也避免两份内容不一致）；
   但需要定 MC 侧日志的清理策略（它自己会按 `log4j` 配置滚动，我们不干预）。
6. **世界的可操作性**：世界 tab 除了列出来，要不要支持删除 / 导出 / 复制？
   存档是用户的数据，误删代价高，倾向「只读 + 打开所在目录」。
